## Purpose

WeFlow CLI is a local-first command-line tool and MCP server for user-authorized WeChat data workflows: local chat queries and exports, official-account daily reading, favorites, knowledge workflows, and an optional local assistant.

## Current Baseline

- Source package version: take it from `package.json` -> `version` rather than from this file - a hardcoded copy drifts silently, and `package-lock.json` must always match it. The npm registry may remain on an earlier version until a maintainer publishes a release.
- Runtime: Node.js 22.13+; Python 3.10+ is required for database and daily-reading workflows. The floor is set by `src/core/sqlcipherCore.ts`, which imports `node:sqlite` at module scope; that builtin exists from 22.5.0 and stops needing `--experimental-sqlite` at 22.13.0.
- Main development command: `npm run dev -- <command>`.
- Compiled/package command: `node cli.cjs <command>`; CLI, MCP, database, export, and assistant services resolve resources from the same package root in both source and compiled layouts.
- Build check: `npm run build`.
- Regression check: `npm test`.
- Downstream data contract: local JSON export is the first compatibility boundary for `she-love-me` and future consumers; see `docs/DATA_CONTRACT.md`.
- Supported focus: Windows WeChat 4.x; Linux WeChat 4.x has an NT database path; macOS requires user-provided local access credentials for initialization.

## Security Baseline

- Process only data the user owns or is explicitly authorized to access.
- Sensitive configuration fields are encrypted at rest with machine- and user-bound AES-256-GCM.
- The daily reader binds to `127.0.0.1`; its API rejects cross-origin mutations, validates local paths, and restricts image proxy requests.
- The assistant denies all senders until `assistantWhitelist` is explicitly configured. Group routing is experimental and remains denied unless the upstream explicitly supplies group metadata, the group and sender are both allowlisted, and the bot is mentioned. New or incomplete configurations use `strict` privacy mode for cloud inference.
- MCP path inputs are constrained to their expected data roots. MCP clients remain trusted local integrations and must be reviewed before configuration.
- The default MCP tool list is read-only: it excludes publishing, messaging, assistant-memory writes, todo mutation, configuration changes, and deletion. Conversation display names must resolve uniquely before chat data is read.
- Public reports and commits must not contain databases, keys, tokens, wxid values, real chat content, or unredacted logs.
- Todo status changes and deletion use a preview/confirm protocol. Machine callers receive `CONFIRMATION_REQUIRED` unless the user-approved execution includes `--yes`.
- AI and database credentials, selected-conversation identifiers, private queries and filters, export locations and display names, and NT scan roots are inherited by workers through environment variables and are not copied into child-process command arguments. Long-lived worker environments clear unrelated internal values before startup.
- `config set-env` and `fav set-key --from-env` provide command-history-safe secret input. Their JSON workflows require a read-only preview followed by explicit `--yes`, and never return secret values or discovered database paths. Bulk clearing of configuration, access lists, or audit history requires interactive confirmation or explicit `--yes`.
- Core JSON reads validate pagination before database access. `messages --start/--end` now applies its Unix-second time range before offset and limit instead of silently ignoring the options.
- `scan --json` and `assistant log --json` return metadata only. They intentionally omit local paths, account identifiers, nicknames, and log content. `evidence-review` requires preview and confirmation, and its machine result omits both analysis text and the output path.
- `init --dry-run --json` exposes a content-free plan. JSON execution returns `INTERACTIVE_REQUIRED`; database verification, directory discovery, key capture, and configuration writes remain an explicit terminal workflow.
- `vault rag` requires a read-only preview and explicit confirmation before reading local knowledge or calling the configured AI provider. The question is inherited by the Python worker through the environment rather than copied into process arguments.
- `search` and `chat` use the same preview/confirmation boundary. Queries, questions, and optional conversation restrictions are inherited through the worker environment instead of appearing in process arguments; machine callers cannot start interactive RAG chat.
- `daily-server --status --json` remains read-only. Machine startup uses `daily-server --dry-run --json` followed by `daily-server --yes --json`; the confirmed process is detached and remains bound to loopback. The legacy `fav-server` compatibility entry enforces the same preview and confirmation rules.

Documentation was synchronized with the current source baseline on 2026-09-19. Command behavior is defined by `bin/weflow-cli.ts`; detached reader startup waits for service readiness, and release packages can lag behind the GitHub source until published.

- **The daily is no longer all-or-nothing.** It fetches every article before writing anything and the bodies lived only in memory, so any interruption threw the whole day away - a 400-article day is over an hour of fetching, and the 2026-09-22 run stopped at 105/403 with nothing written. The relative cost of the remaining parts is unchanged, so the throttle is now the largest single line item.

because nobody built it" look identical to a reader.
- The stored corpus under `output/biz-daily/` shows **two README generations**, and no code in the repository produces the older one (checked by searching every README writer: the only ones left are `biz_daily` and `fix_topics`, and both emit tables). The older generation - the numbered list, on the eight days 2026-08-27..09-03 - rendered **every article link's text as `---`** (1446 links across those days, the only well-formed entry being the `行动建议` one). That text has been repaired in place from each target file's frontmatter title, leaving the numbered format, the entry order and the recorded counts untouched, with each original kept as `.README.before-title-repair.md`. The counts were **not** changed even where they differ from the directory (226 in the README vs 228 articles on 08-27, 205 vs 217 on 08-30): a README count describes the run that wrote it, whereas the folder accumulates, so "they disagree" is not by itself an error.
- Two days whose `.articles.json` was effectively absent were rebuilt from their md files: 2026-08-27 held 33 entries against 228 articles (14%) and 2026-08-30 held 0 against 217. Both are marked with a `reconstructed` block naming the reason, the recovered fields and what was excluded, and the originals are kept as `.articles.before-reconstruction.json`. The **topics are copied from the md and verified** - every entry agrees with the "one topic per source across days" map (228/228 and 217/217), which is what makes copying legitimate here; on 2026-09-05 the same check fails, so that day's unclassified articles are recorded as **unknown (`""`) rather than as the md's `学术` fallback**. The `行动建议.md` report artifact is excluded from all of these, on the same `url:`-in-frontmatter test the search paths use - the first attempt at the rebuild included it as an article.
- **Every stored day's `.articles.json` now describes that day's articles, and the convention it follows was recovered from the days that were never rewritten rather than assumed.** That convention has three parts, and all three were needed before the six rebuilt days matched the six untouched ones: the JSON **excludes the `收藏/` collection** (a separate set, synced by its own command - read off 2026-08-25, whose 186 entries are its 184 articles plus 2 orphans, not its 197 files), **excludes report artifacts** like `行动建议.md` (the article predicate is `url:` in the frontmatter, the same test the search paths use), and **includes entries whose md was never written** because the body was too short - `biz_daily` prints `[SKIP] 内容过短` and skips the file while still recording the article, so an entry with no file on disk is expected rather than a dangling pointer. Checked across all twelve days: no article on disk is missing from the JSON, no favorite is in it, and the only entries without a file are those short-content orphans (08-24 has 2, 08-25 2, 08-28/09-02/09-04 1 each, 08-29 2). Six days were rebuilt from their md (2026-08-24, 08-27, 08-28, 08-30, 08-31 and 09-05), each carrying a `reconstructed` block with the reason, the recovered fields, the scope, and the topic verification - and each keeping its original as `.articles.before-reconstruction.json` (09-05's as `.articles.overwritten-by-accidental-run.json`) with its `generated_at` preserved in the new file. **Two mistakes were made and corrected inside this work, and they are the same class**: the first rebuild counted `行动建议.md` as an article, and the first rebuild of four days also pulled in the `收藏/` copies and dropped the short-content orphans - that is, it quietly changed what the file *means* instead of completing it. Both were caught by checking the rebuilt days against the untouched ones. 2026-09-04 is left exactly as it was: its 178 empty topics are the record of the failure this session fixed, and rewriting it would destroy the evidence.
- **Jev cannot rank conversations for search, and this is measured rather than assumed.** The first design of `route_cards` put one card per conversation (type, message count, span, recency, name, query-term hit counts) into a single request and asked Jev which ones were relevant. Both question shapes failed: as a per-card `noul` every candidate landed at 0.50-0.51 (a coupon group with one message sat in the same band as the conference group with 213 hits, and the model left out the session that most deserved opening), and as a per-card `score` on a 0/1/2 scale all 20 candidates scored 1.74-1.76 regardless of whether they had 247 hits or 8. Sorting the same data locally by hit count ranked it correctly. The card simply carries too little for the judgement being asked (the model has never seen the conversation), so the shipped tool **ranks locally and keeps Jev only for the one job it does well**: choosing the real query words from the n-gram fragments. A second `noul` finding is recorded with it - the answer is a **probability float** (0.98 for a true claim, 0.01 for a false one), so reading it as a boolean makes every question look answered "no"; the run printed "it thinks none of these words are what you want" when the truth was that the parser read the wrong field.
- **A limited run still writes a README that describes the whole directory.** `biz_daily`'s README and its `今日简报` are built by scanning the day's existing `.md` files, not from the articles that run fetched, so `--limit 6` on a day that already holds 191 articles rewrites the index for all 191 and reports `共 191 篇推送`. This is not a bug (the README is supposed to describe the day's folder) but it is misleading as a check: a limited test run leaves no trace of its own limit in the README, and the only sign is the count. Use the run's stdout progress lines - not the README - to tell what a partial run actually fetched.
- **`tags` is the configured category for any source that has one, by design.** The prompt for a categorised source is summary-only and explicitly says *不要输出主题、标签、相关度或概念字段*, and the code sets `tags = [category]` itself. Measured over the 1584 articles of the 11 stored days: 1396 carry exactly `[topic]`, 182 carry none, and only **6** carry real extracted tags - and those 6 are the corpus built without configured categories. The checkable signature is that **on every one of those days each source maps to exactly one topic** (36/40/15/43/41/27/35/36/3/36/6 sources, no exceptions), which is what topic-from-config produces and per-article classification does not. A live call through the production prompt returns real tags (`AI与数学, 人类数学家, 数学共同体, 人机关系, 学术人文`), so extraction itself is not broken - it is simply not asked for on that path. Practical consequence: to get meaningful tags for a source, leave its category unconfigured (and accept that its topic then comes from classification rather than from you).
- **No real artifact on disk carries `includeScore`.** The six files in the 2026-09-05 output directory were written before that field existed, so the field has never been produced in a real run - which is why calibration has to re-score articles rather than read stored values.
- The report's admission threshold (`INCLUDE_THRESHOLD = 0.5` on `includeScore`) is provisional in the same way and, unlike the old rule, it is actually applied: both loaders call one predicate. Turning it on **reduced** what the report collects, because the primary loader previously collected everything unfiltered. On a 6-article trial the scores straddled the cut point (0.48 and 0.63 on two engineering posts), so the cut point is doing real work rather than being decorative.
- Message reads select only the columns the reader consumes, resolved per shard from what that shard actually has. `nt_decrypt` reads six (`local_id`, `server_id`, `local_type`, `real_sender_id`, `create_time`, `message_content`) and a WeChat version that renames or drops any other column of the message table therefore cannot make a shard unreadable. What is lost is reported, not swallowed: a shard lacking one of those six is read anyway and named in `missingColumns`, while a shard where none of them is present is reported as `SCHEMA_MISMATCH` and makes `coverage` partial. `export_chat_html` reads rows positionally, so there a missing column keeps its slot as `NULL` instead of shifting the fields after it. Both are verified against synthetic shards only - no future WeChat schema has been tested.

- **Topic exclusion is a display-layer switch, and that is a measurement result rather than a preference.** `dailyExcludeTopics` (or `--exclude-topics`) removes a topic from the daily report and the reader page; the article is still fetched, judged and archived. Filtering *before* the fetch was the original ask and was rejected on evidence: from a source name plus a title and the platform digest - everything that exists pre-fetch - the type judgement agreed with the source-level configuration on only **60%** of 217 articles, with 48 false positives, and there is no gold standard either way. A dropped fetch is irreversible (nothing is archived, and the page is not the same weeks later) while an unwanted article costs only attention, so the decision is deliberately placed where it can be undone by regenerating. The exclusion is orthogonal to `--include-all` and to the inclusion score, and **all three lists in 我拿不准的 are filtered** - passing the exclusion set to `admits()` in the "not admitted" list had the opposite effect and surfaced the excluded articles (that list is populated by exactly the articles being excluded). One predicate (`is_excluded_topic`) now serves both directions. Excluding the focus topic is refused with a WARN, because the result is not an empty report but a misleading one: it exits with "未找到文章，请先运行 biz_daily.py". The key is registered in all four `configService` literals plus `bin`'s `configurableKeys`, which `test/config-keys.test.ts` now enforces - a key missing from defaults or `clear()` survives `config set` and then quietly disappears.
- **The source-level prior is recorded, never acted on.** Every daily appends `(source, topic)` counts for the articles it archived to `~/.weflow-cli/source_topics.json`, and names the sources whose history is stable and lands in an excluded topic (`来源先验: 甲号 → 新闻（20 篇里 19 篇 = 95%）`). **Nothing is skipped.** The table has to be measured rather than authored - the pre-fetch guess it replaces was already measured at 60% - so recording is a prerequisite for a future skip decision, not that decision. It lives outside the repository because it holds 公众号 names (a test asserts this), counts are append-only, and only articles that landed on disk are recorded, so the table and `output/` describe the same corpus. Thresholds (8 samples, 80% share) are **provisional and uncalibrated**. `stable_source_topic` returns `None` for "not enough history yet", and callers must not read that as a default topic - skipping a source *because* it is unknown is the worst failure available here. Whether a stable source is ever skipped before the fetch remains the user's call, to be made on the printed numbers.
- Skills are **not** an extension mechanism in the capability sense: installing one adds no tool, executes no code, and
  reaches no configuration, database or arbitrary file. `read_skill` can only return a file named `SKILL.md` that a
  directory scan already produced, so a traversal-shaped id (`../config.json`) is not a path at all - asserted case by
  case. Symlinked skill directories **are** followed, deliberately (developing a skill in a checkout and linking it in
  is a normal workflow, and the link is placed by the user); this is a known and accepted behaviour, not a gap. The id
  rule is wider than the Anthropic Agent Skills specification on purpose - that spec would reject 5 of the 28 skills on
  the development machine - so an id like `clz_docx_to_mp` is usable and warned about rather than refused. There is no
  installer, no update path and no per-agent deployment: the roots are read, not written. `read_skill` truncates a body
  at 8 KB and says so.

- Scene matching deliberately covers **three** tiers, not four: the reference implementation's sender-fingerprint tier
  (Jaccard over the people who speak in a group) is not implemented, because this project has no service-layer query
  that lists a conversation's participants - `wcdbCore.getGroupMembers` exists but has no caller, so the tier would cost
  a database read on every turn, and the explicit binding already covers the stable case. An ambiguous keyword match is
  refused rather than resolved. Scenes are keyed by `userId`, which equals the conversation id on the WeChat path but
  collapses to the literal `'mcp'` on the MCP path, so there is no per-conversation binding there.

- The assistant can now cause two kinds of outbound effect from an untrusted input (a chat message). `fetch_article` is allowlisted to credential-free HTTPS on `mp.weixin.qq.com` **and re-checks that allowlist on every redirect hop** (asserted on the `redirect: 'manual'` option, because a stubbed fetch cannot observe the runtime following a redirect internally - that gap was found by a mutation check). `search_public` has **no guard and no confirmation gate**: its URL is a constant, so no allowlist applies, and the model's query leaves the machine to a third-party search engine with no preview. That is an accepted risk, chosen explicitly, and recorded in D-058 - do not describe this surface as "no egress" anywhere.

- `set_todo_status` is the only model-callable write besides `export_chat`, and it is deliberately **not** on the MCP surface ("mutating todos stays out"): the chat/panel path can flip one existing todo between done and pending with no preview, while an MCP client cannot reach it at all. It cannot create, delete or edit any other field, and an ambiguous task-text match is refused rather than resolved.

## Current Priorities

1. Keep initialization and database access compatible with supported WeChat 4.x variants, with reproducible issue diagnostics that contain no secrets.
2. Keep the daily reader reliable for configured sources and categories without widening access to local data.
3. Maintain security boundaries around local servers, assistant access, MCP tools, and cloud AI disclosure.
4. Evaluate external collaboration through read-only, synthetic-data, versioned interfaces before connecting real user data.
5. Make Bot-channel send capability and its limitations unambiguous in CLI naming and help text before extending messaging features.

## External Collaboration Position

For projects such as Yance, WeFlow CLI remains an independent local data-access layer. Early collaboration may cover read-only schemas, anonymized fixtures, and controlled MCP adapters. It must not require sharing real databases, credentials, keys, full local directories, or direct database access by an external product.

Where outside code attaches is stated rather than implied (D-048): **in-repo contribution, or MCP/`--json` from a
separate process.** There is no plugin loader, no adapter registry and no public import surface, and that is a boundary
decision, not an unfinished chore - an in-process plugin would hold the same reach as the code it joins. `docs/EXTENDING.md`
is the checklist for the in-repo path, including the two extension points where **nothing** will fail if you forget a
step (the CLI's interactive-menu entry is the notable one).
