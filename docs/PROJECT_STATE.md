# Project State

> Last reviewed: 2026-09-21 (daily article classification moved to a decision model). This is the current maintenance snapshot, not a release note. Keep it factual and update it with meaningful project changes.

## Purpose

WeFlow CLI is a local-first command-line tool and MCP server for user-authorized WeChat data workflows: local chat queries and exports, official-account daily reading, favorites, knowledge workflows, and an optional local assistant.

## Current Baseline

- Source package version: take it from `package.json` -> `version` rather than from this file - a hardcoded copy drifts silently, and `package-lock.json` must always match it. The npm registry may remain on an earlier version until a maintainer publishes a release.
- Runtime: Node.js 22.13+; Python 3.10+ is required for database and daily-reading workflows. The floor is set by `src/core/sqlcipherCore.ts`, which imports `node:sqlite` at module scope; that builtin exists from 22.5.0 and stops needing `--experimental-sqlite` at 22.13.0.
- Main development command: `npm run dev -- <command>`.
- Compiled/package command: `node cli.cjs <command>`; CLI, MCP, database, export, and assistant services resolve resources from the same package root in both source and compiled layouts.
- Build check: `npm run build`.
- Regression check: `npm test`.
- Downstream data contract: local JSON export is the first compatibility boundary for `she-love-me` and future consumers; see `docs/DATA_CONTRACT.md`.
- Supported focus: Windows WeChat 4.x; Linux WeChat 4.x has an NT database path; macOS requires user-provided local access credentials for initialization.

## Security Baseline

- Process only data the user owns or is explicitly authorized to access.
- Sensitive configuration fields are encrypted at rest with machine- and user-bound AES-256-GCM.
- The daily reader binds to `127.0.0.1`; its API rejects cross-origin mutations, validates local paths, and restricts image proxy requests.
- The assistant denies all senders until `assistantWhitelist` is explicitly configured. Group routing is experimental and remains denied unless the upstream explicitly supplies group metadata, the group and sender are both allowlisted, and the bot is mentioned. New or incomplete configurations use `strict` privacy mode for cloud inference.
- MCP path inputs are constrained to their expected data roots. MCP clients remain trusted local integrations and must be reviewed before configuration.
- The default MCP tool list is read-only: it excludes publishing, messaging, assistant-memory writes, todo mutation, configuration changes, and deletion. Conversation display names must resolve uniquely before chat data is read.
- Public reports and commits must not contain databases, keys, tokens, wxid values, real chat content, or unredacted logs.
- Todo status changes and deletion use a preview/confirm protocol. Machine callers receive `CONFIRMATION_REQUIRED` unless the user-approved execution includes `--yes`.
- AI and database credentials, selected-conversation identifiers, private queries and filters, export locations and display names, and NT scan roots are inherited by workers through environment variables and are not copied into child-process command arguments. Long-lived worker environments clear unrelated internal values before startup.
- `config set-env` and `fav set-key --from-env` provide command-history-safe secret input. Their JSON workflows require a read-only preview followed by explicit `--yes`, and never return secret values or discovered database paths. Bulk clearing of configuration, access lists, or audit history requires interactive confirmation or explicit `--yes`.
- Core JSON reads validate pagination before database access. `messages --start/--end` now applies its Unix-second time range before offset and limit instead of silently ignoring the options.
- `scan --json` and `assistant log --json` return metadata only. They intentionally omit local paths, account identifiers, nicknames, and log content. `evidence-review` requires preview and confirmation, and its machine result omits both analysis text and the output path.
- `init --dry-run --json` exposes a content-free plan. JSON execution returns `INTERACTIVE_REQUIRED`; database verification, directory discovery, key capture, and configuration writes remain an explicit terminal workflow.
- `vault rag` requires a read-only preview and explicit confirmation before reading local knowledge or calling the configured AI provider. The question is inherited by the Python worker through the environment rather than copied into process arguments.
- `search` and `chat` use the same preview/confirmation boundary. Queries, questions, and optional conversation restrictions are inherited through the worker environment instead of appearing in process arguments; machine callers cannot start interactive RAG chat.
- `daily-server --status --json` remains read-only. Machine startup uses `daily-server --dry-run --json` followed by `daily-server --yes --json`; the confirmed process is detached and remains bound to loopback. The legacy `fav-server` compatibility entry enforces the same preview and confirmation rules.

Documentation was synchronized with the current source baseline on 2026-09-19. Command behavior is defined by `bin/weflow-cli.ts`; detached reader startup waits for service readiness, and release packages can lag behind the GitHub source until published.

## Active Constraints

- Issue #7 remains open pending reporter verification. HTML emoji export preserves the emoji label and matches resource records only by nonzero server-message identity; local IDs are not unique across shards or conversations. WeChat 4.x V2 image containers are decoded with an account-specific media key derived from local `kvcomm` data and verified against a real cached V2 header. Remote emoticons use AES-CBC with the message key as both key and IV. Entity-escaped emoji XML is normalized before extracting MD5 and media URLs; failed encrypted downloads fall back across available thumbnail/CDN fields. Signature-only default `[打脸]` messages use the bundled official Facepalm asset when no message-specific resource is available. Forwarded app cards remain structured links with available covers, and Bilibili share pages can resolve covers through their BV metadata endpoint when no `og:image` is present. Forty-two synthetic Python regression tests (`export_chat_media_test.py`, `export_chat_media_report_test.py`) cover these paths; run `python -m unittest discover -s test -p '*_test.py' -v`. CI also runs these tests. This does not establish compatibility with every real WeChat media format.

- WeChat platform behavior, database formats, account restrictions, and terms can change without notice. Local operation is not a legal, account-safety, or platform-compatibility guarantee.
- **The daily is no longer all-or-nothing.** It fetches every article before writing anything and the bodies lived only in memory, so any interruption threw the whole day away - a 400-article day is over an hour of fetching, and the 2026-09-22 run stopped at 105/403 with nothing written. Bodies are now cached under `output/.cache/fetch/` keyed by URL, so a re-run fetches only the missing ones (measured: a resumed batch of 3 goes from 64 s to 2.0 s, and cache hits take **no** throttle sleep because they send no request - the throttle exists to spare the upstream, and this is the same direction). Only successes are cached, so a failure is retried next time rather than remembered. `--no-fetch-cache` forces a refetch. **The lesson that made this urgent**: a long single-shot run is a gamble, and `cmd | tee log` reports the wrapper's exit code, not the program's - the 105/403 failure looked like `exit 0`.
- Where a many-source day spends its time is now measured rather than assumed, and two of the three biggest items have been fixed. A 190-article day **was** ~3 h 10 m: fetching bodies ~130 min, the deliberate 8-12 s inter-article throttle ~32 min, image downloads ~18 min (47 image links per three articles, 0.37 s and 135 KB each, sequential), and the serial summary loop ~9 min (measured 2.27/2.92/2.45 s per article, plus 0.3 s each). It is now ~1 h 5 m: fetching ~33 min (gzip, below), throttle ~32 min, images ~3 min (6-way concurrent), summaries ~2 min (6-way concurrent). Classification was never a factor - already concurrent. **The throttle is now the largest single item, and it is the one thing left that is deliberate** ("reduce upstream pressure"); the other two costs were implementation choices, not policy. Both new concurrency settings are 6 (`IMAGE_WORKERS`, `SUMMARY_WORKERS`), matching `JEV_WORKERS`.
- **Article bodies are now fetched with `Accept-Encoding: gzip, deflate`**, which `urllib` does not send by default. Measured on the same four articles: 3.3-3.5 MB and 33-40 s before, 0.7-0.8 MB and 6-10 s after, with the decompressed page identical in size and `js_content` / `rich_media_content` still present - so ~130 min of fetching becomes ~33 min on a 190-article day, and **fewer bytes cross the wire than before**, which is the same direction as the throttle. `_decode_body` recognises only the two encodings the request asks for, and passes anything else through unchanged: raising there would turn a transfer optimisation into a fetch failure. The relative cost of the remaining parts is unchanged, so the throttle is now the largest single line item.
- The article body is **not** available locally, so fetching cannot be skipped: a 公众号 message in the local database carries title, digest, URL and metadata, and stripping its XML tags leaves 0 Chinese characters (the ~5-12 KB that remains is URLs, base64 and ids).
- The OC Bot channel is separate from a personal WeChat message stream. `send` can only reply through an already established Bot-channel conversation with a valid context token; it cannot initiate messages to existing personal contacts, post as the user's personal account, or send into ordinary personal WeChat groups.
- The current official OC/iLink payload model has not been verified to support group events or group invitations. The project does not implement client automation or protocol bypasses to add a bot to groups.
- Cloud AI workflows may transmit user-selected, privacy-filtered input to the configured provider. Local inference avoids that network transfer.
- `vault promote ideas` and `vault promote all` run without AI by default. AI generation requires explicit `--with-ai` and an API key. CLI execution also requires preview and confirmation. `vault init` creates both the existing article-sync folders and the structured directories required by promotion workflows.
- `vault init`, semantic-index construction, the knowledge pipeline, and report generators require preview and confirmation for machine execution. Preview JSON contains counts and behavior flags but omits local paths, conversation names, and generated content.
- Automatic data-directory discovery checks common user locations only. Cross-drive name search requires `init --search-drives`; structural disk search requires `init --full-scan`. Both can be slow on large, removable, or network-attached volumes.
- Dependency audit findings must be reviewed before dependency upgrades; do not run breaking `npm audit fix --force` without validation.
- The WCDB native query entry point has no parameter-binding ABI. Calls that supply parameters are rejected rather than falling back to interpolated SQL; existing internal callers are unchanged.
- The daily report classifies article topic and relevance by calling a decision model (`api.typesafe.ai`) when `typesafeApiKey` is set, so article titles and bodies leave the machine. Article text already went to the configured LLM for summarisation, so this is an additional vendor rather than an additional category of data; `daily --no-ai` is the way to keep everything local. The switch was made on the strength of a 60-article comparison against the stored labels, **not against a gold standard** - the stored labels are the previous model's own output, and a hand-labelled sample is still owed. `--classifier llm` reverts in one flag.
- The decision-model calls now record **which model actually served them**, and validate the `choice` contract on the way in. Two facts were verified against the live API rather than taken from a source reading: `instructions` may be a **structured object** (`{"goal": …, "rules": […]}`) and not only a string, and every response carries a `model` field naming the **served version** (`jev-1.13.0`) as distinct from the requested alias (`jev-latest`). That name is now in `usage['model']` and on `JevClient.last_model`, and the daily stores it as a top-level `decisionModel` in `.articles.json` - the point is to make "production is no longer running what was measured" visible, because an alias that drifts produces results that look fine. Every `choice` answer is now checked before it is used: probabilities present, key set equal to the criteria, values in `[0,1]`, sum ≈ 1, and `choice` equal to the argmax. The argmax check is the one that matters - a non-argmax choice is not a wrong-looking answer but a completely normal-looking wrong one, the same failure shape as reading `noul` as a boolean. Because a check that rejects a *legitimate* response would make the daily fall back to the old LLM path silently, it was exercised rather than asserted: 14 real articles sampled across days and sources all passed, all served by `jev-1.13.0`, with relevance spanning 0.38-1.41 and inclusion 0.15-0.81. That is a spot check on one machine, not a guarantee about the model's future output; a rejection at run time is reported per article and degrades to the previous path.
- **The LLM is no longer asked to classify when the decision model already has.** The summary prompt carried `【主题】`/`【相关度】` plus the six-category criteria and three-level definitions whoever was judging, so on the Jev path those were generated and discarded: 446 characters of prompt per article (57% of the prompt skeleton, ~9% of total input since the body dominates) and 10-15 output tokens. `SUMMARY_ONLY_PROMPT` drops exactly those sections and a test asserts the **summary/tag/concept requirements are byte-identical** between the two prompts, which is what keeps the change from altering the output rather than just its cost. The switch is **per article**: `--classifier llm` and any article whose judgement failed still get the full prompt, because those need the LLM's own topic and relevance - so the fallback path stays byte-identical per D-031. Savings are estimated from prompt size and output fields; neither client exposes billed usage.
- **Judging no longer requires generating.** `daily --no-summary` keeps the decision model for topic/relevance/inclusion and skips every LLM call inside the daily step, so a machine with no DeepSeek key can still classify. Two things make it honest rather than convenient: the LLM-key checks had to be relaxed in **both** callers (`biz_daily` and `pipeline`), because they encode "Phase 2 needs an LLM key" - a claim that stops being true once nothing is generated; and the artifacts must not imply a summary that does not exist, so the md omits the `## AI 摘要` section entirely and `.articles.json` records `summary: ""` (an empty heading reads as a failed generation, the platform digest reads as our summary - both would be claims about something absent). Tags fall back to `[topic]`, the convention that already covers "no tags were extracted". The scope is deliberately the daily step only: the pipeline's later steps (action suggestions, wiki compile, AI report) still call an LLM and say so at runtime; a fully LLM-free run combines it with `--skip-classify --skip-wiki --skip-ai-report`. Verified with a deliberately invalid DeepSeek key: the run completes with no 401, so nothing reached the LLM.
- **The decision model's free period ends 2026-09-25**, after which input tokens are billed (output has been free during the promotion). Anything expensive to re-measure should be measured before then, or the cost of a re-run should be assumed. The client only ever sees token counts, not a billed amount, so cost stays an estimate from tokens times price - the same position the reference implementation (`browser-use` × TypeSafe) documents.
- Relevance in the daily report is split into 高/中/低 at cut points that are **provisional** (0.5 and 1.5 on a `[0,2]` score). The raw score is stored as `relevanceScore` so recalibrating does not require re-running a day. On a 6-article trial with the shipped criteria, nothing reached 高.
- Search reranking is fail-soft by design: no key, a network failure or an overloaded service (`HTTP 529` was observed live) all return the first-stage order with a warning. Its one real hazard is candidate numbering - a model that answers question `c3` against candidate `c5` sinks the best hit with no error at all - so every candidate is labelled in the state and a separate single-choice question cross-checks the argmax, warning on disagreement. Verified on real data before shipping, but only on one planted query.
- `build_index` had never indexed any article (`glob(' marriage*.md')` matched 0 of 188 files), so semantic search covered chat messages only. The glob is fixed; **the article corpus will enter the index on the next rebuild**, which spends embedding calls, so it is a deliberate action rather than a side effect.
- Every config key a script reads is declared in `CliConfig`, so `config set` can set it; `test/config_keys_declared_test.py` enforces this with a justification-required exception list. Two keys were found by that audit: `dashscopeApiKey` (read by two scripts, absent from the schema entirely) and `favPassphrase` (a first-class encrypted secret that the allowlist refused). Both are settable now, and `dashscopeApiKey` became encrypted.
- `bizKey` / `bizSalt` are read by three scripts and written by nothing, so that branch is unreachable and `biz_message_0.db` is always opened via the key derived from `favPassphrase`. Recorded rather than "fixed": adding config surface for a value nothing produces would be inventing a knob, not restoring one.
- No script reads a `configService.ENCRYPTED_KEYS` member without decrypting it; `test/encrypted_config_test.py` enforces this statically (accepting the `*_enc` hold-then-decrypt convention). Four scripts used to read `deepseekApiKey` raw. They worked only because that one key is plaintext on the development machine - every other encrypted key on disk is `lock:` ciphertext, so a routine `config set` of that key would have broken all four at once with an error that named the wrong cause.
- **`assistant start` had never once started the daemon on the machine this was developed against.** The child was spawned without `--yes` while `assistant run` confirms through `inquirer` on a stdin the daemon had set to `ignore`, so the child died on the prompt while the parent printed「✓ 守护进程已启动 (pid …)」and wrote a pid file - and `~/.weflow-cli/` contained **no `assistant.log` and no `assistant.pid` at all**, which is how the documented `assistant start` flow turned out never to have completed. The env marker that appeared to guard this was read by nothing and was built as an env **key** containing `=` (`'WEFLOW_ASSISTANT_DAEMON=1'`). Both are gone (D-039): the parent confirms and passes `--yes` explicitly, and success is now **observed** - the child is watched for 700 ms, a dead one is reported with its exit code and the log tail, and no pid file is written. Verified live: it reports `子进程启动后立即退出 (code 1)；日志尾部: Error: 未登录消息通道, 先运行 weflow-cli login-wechat`, i.e. the actual blocker - **the message channel is not logged in** (`wechatOcToken` unset) and the sender allowlist is empty, so even with a channel it would deny every sender.
- The daemon runs `dist/bin/weflow-cli.js` **when that file exists**, so a source change does not reach the daemon until `npm run build` runs. Rebuilding is also what makes a daemon test meaningful: before this, the child was a compiled snapshot of the daemon logic.
- "Is this a real article" has one predicate: the frontmatter carries `url:`. Generated artifacts (`README.md`, `行动建议.md`) appear at both `<day>/` and `<day>/<topic>/`, so path-based filtering misses half of them. Both search paths (index building and the keyword fallback) now agree; the fallback previously returned report artifacts as articles.
- Nothing declared in `scripts/` describes behaviour the code does not have. A sweep removed `MAX_ARTICLES` (a fetch cap that was never read), a duplicate `CONFIG_PATH`, `_utils.parallel_map` (no callers), and fifteen unreachable lines after `search()`'s return that documented a `dict` return the function no longer has. A constant whose comment lies is worse than no constant - this is the same failure shape as a field written on one path only.
- A sweep of `scripts/*.py` (compare every top-level function by name and source) finds **25 groups of same-named functions in more than one file, of which all but one differ**. Two of those groups are worth knowing about and neither is fixed:
  - `get_name_map` + `open_db` exist in **six** copies each and are **semantically identical** (differences are whitespace and `except: pass` formatting), so they are safe to unify. Deferred: the shared version needs a lazy sqlcipher loader, and three test files stub `sqlcipher3` at *import* time — a lazy loader would resolve it at call time, outside the patch, and open the plain-SQLite fixtures with the real driver.
  - `parse_frontmatter` exists in **four** copies and they are **not equivalent**: `_utils` keeps the body with `lstrip('
')` and only unquotes when both ends carry the same quote character, while the other three use `strip()` and `strip('"').strip("'")`. Unifying therefore **changes what three commands produce** (leading whitespace in bodies, values with mixed quotes), so it needs a deliberate choice rather than a tidy-up.
- The same sweep over the TypeScript side (`src/**`, `bin/**`, ~18.8k lines) finds **5 same-named groups, and none of them is a defect** - recorded so the next sweep does not have to re-open them. Two were false positives from matching local assignments (`content`, `summary`). `resolvePackageRoot` is the **correct** shape: one implementation in `src/utils/packageRoot.ts` that walks up looking for `package.json` **and** `scripts/`, with `bin/weflow-cli.ts` and three services importing it and wrapping it in one-line local aliases. And the two talker resolvers differ **deliberately**: `talkerUtils.resolveTalker` is the CLI path (server-side search, interactive pick when a name is ambiguous, throws when non-interactive), while `assistantTools.resolveUniqueTalker` is the assistant path (no prompt is possible, so ambiguity always throws) and returns the query unchanged when nothing matches. That last fallback is benign rather than a silent wrong lookup: its only caller does `getMessages(talker)` and reports `(没找到「X」的消息)` from the empty result, so a mistyped name ends in an accurate "not found" instead of a wrong conversation.
- A scan for **string collections written in more than one file** (the `TOPIC_ORDER` shape, which is what the topic fallback bug turned out to be) finds three, and two were real. Both are now single definitions. `MESSAGE_ANCHOR_COLUMNS` moved into `nt_common` - it is the shared NT plumbing that module exists for, and it had **three** copies (a named one, a literal in the same file's `ORDER BY`, and one in the exporter). Its **order is behaviour**: the same tuple is used as a set for the schema check and as the `ORDER BY` key list, so putting `local_id` first would silently reorder every conversation read. It stays a tuple rather than a set (a set would let the order follow the interpreter's hash seed), and a test pins `create_time` as the primary key, the tuple type, and the absence of the literal in both readers. The relevance vocabulary `['低','中','高']` moved to `_utils` beside `TOPICS`, with `DEFAULT_RELEVANCE` naming the fallback that answers why the corpus once read 中 everywhere - it is the value every failed classification path lands on, and 中 reads as a *positive* judgement rather than "not judged". `extract_todos.py`'s identical `['高','中','低']` is deliberately **not** coupled: that is the `--urgency` vocabulary for todos, a different concept that merely shares three characters, carried as a documented exception in the check.
- Several checks added in this pass were written from an assumption rather than from the code, and each is the same mistake worth naming: asserting `jev_client.DEFAULT_RELEVANCE` exists (it does not - `score_to_relevance` always has a level to return, so it needs no fallback); searching the source text for the JSON writer's `tags` default, which flagged the docstring that documents that very pattern; and checking `relevance`'s inline vocabulary by confirming only that the module *imports* it - a mutation test proved "imports the table but writes the literal anyway" sails through an identity assertion, so that check now looks for the literal itself, with a justification-required exception list (the convention `test/config_keys_declared_test.py` already established).
- NT plumbing that two readers need (`discover_message_shards`, `derive_database_key`, `table_columns`) lives only in `scripts/nt_common.py`; both `nt_decrypt` and `export_chat_html` import it, and a test pins it by identity. They used to be four same-named helpers with different contracts - one `discover_message_shards` returned `[the configured database]` when it found no shards, the other returned empty and left the compensation to its caller.
- The topic taxonomy (`TOPICS` and `TOPIC_CRITERIA`) lives only in `_utils`; the prompt path and the decision-model path read the same table. It used to be copied into six files, and the copy inside the prompt had drifted to five categories while `TOPICS` held six - 政治 has 26% of the corpus and had no judging rule.
- One article gets one topic, decided once. The write path used to derive an article's topic from three places - the folder-grouping key (defaulting to `'学术'`), the JSON writer (defaulting to `''`), and the raw field - so one run could emit `topic: 学术` in the md and `topic: ""` in the JSON, with no error on either side. The 2026-09-04 output is that failure in full: 178 articles, all under `学术/`, all `topic: ""` in `.articles.json`, and two of them are "OpenAI 深夜发布 GPT-6 Astra" and an AI-tool launch. The trigger is ordinary rather than exotic - `daily --no-ai`, or a daily run with no API key, skips the classification phase entirely, so no article has a `topic` key at all while the write phase still runs. `_utils.DEFAULT_TOPIC` is now the only fallback, and `biz_daily._group_by_topic()` both normalises and groups in one entry point - so the md frontmatter topic (which is the *group key*) and the JSON topic cannot be different values by construction. It checks **membership** in `TOPICS` rather than emptiness, and reports the count when it fires so a whole-batch fallback cannot read as a normal classification. The **same shape, seven lines away, sat in `tags`** and was fixed in the same pass: the md writer defaulted a missing `tags` key to `[topic]` and the JSON writer to `[]`, so the same articles read `tags: ['学术']` in the md and `tags: []` in the JSON - measured on 09-04 (177 articles) and on no other day, because the 1408 articles of the eight normally-generated days agree completely. Both writers now call `_tags_for_write`, which keeps a *present but empty* list empty (the model extracted no tags is a different case from the key being absent, and merging them would just be a new default written in two places). The field-by-field check of everything both writers carry is now **exhausted** for this writer pair: `relevance` matches on 1591 of 1593 comparable articles (the two exceptions were the 2026-09-05 residue of an accidental local run; that day's `.articles.json` has since been rebuilt from its md files, so re-running this comparison no longer shows them), and `title` / `source` / `date` / `url` come from the same source values. `summary` looks like it disagrees on 79 articles, but that is not a live path: both writers read the identical expression (`biz_daily.py` lines 158 and 996), and the mismatches are day folders whose md and json were written by **different generations of the pipeline** - the md carries the older `## 深度解析` structured summary while the JSON carries the current prose one. The same folders show it more starkly: 2026-08-27 has 196 md files with no JSON counterpart and 2026-08-30 has 218 with the JSON holding zero entries. Regenerating those days is what would make them consistent; it is not a code defect. The fallback value is still a **guess**: the honest label for these articles is "unclassified", and introducing a real `未分类` category would change the folder layout, the HTML sections and every literal topic comparison, so it is not done. `TOPIC_ORDER` is still copied verbatim into four scripts that iterate it to lay out report sections; those are deliberately **not** unified - `create_reading_notes` and `generate_html` have no `_utils` import edge, so adding one makes whether the command runs depend on the caller's working directory - so `test/default_topic_test.py` asserts all four copies still equal `TOPICS`. Adding a seventh category now fails the tests instead of silently dropping a section from the report.
- The stored corpus under `output/biz-daily/` shows **two README generations**, and no code in the repository produces the older one (checked by searching every README writer: the only ones left are `biz_daily` and `fix_topics`, and both emit tables). The older generation - the numbered list, on the eight days 2026-08-27..09-03 - rendered **every article link's text as `---`** (1446 links across those days, the only well-formed entry being the `行动建议` one). That text has been repaired in place from each target file's frontmatter title, leaving the numbered format, the entry order and the recorded counts untouched, with each original kept as `.README.before-title-repair.md`. The counts were **not** changed even where they differ from the directory (226 in the README vs 228 articles on 08-27, 205 vs 217 on 08-30): a README count describes the run that wrote it, whereas the folder accumulates, so "they disagree" is not by itself an error.
- Two days whose `.articles.json` was effectively absent were rebuilt from their md files: 2026-08-27 held 33 entries against 228 articles (14%) and 2026-08-30 held 0 against 217. Both are marked with a `reconstructed` block naming the reason, the recovered fields and what was excluded, and the originals are kept as `.articles.before-reconstruction.json`. The **topics are copied from the md and verified** - every entry agrees with the "one topic per source across days" map (228/228 and 217/217), which is what makes copying legitimate here; on 2026-09-05 the same check fails, so that day's unclassified articles are recorded as **unknown (`""`) rather than as the md's `学术` fallback**. The `行动建议.md` report artifact is excluded from all of these, on the same `url:`-in-frontmatter test the search paths use - the first attempt at the rebuild included it as an article.
- **Every stored day's `.articles.json` now describes that day's articles, and the convention it follows was recovered from the days that were never rewritten rather than assumed.** That convention has three parts, and all three were needed before the six rebuilt days matched the six untouched ones: the JSON **excludes the `收藏/` collection** (a separate set, synced by its own command - read off 2026-08-25, whose 186 entries are its 184 articles plus 2 orphans, not its 197 files), **excludes report artifacts** like `行动建议.md` (the article predicate is `url:` in the frontmatter, the same test the search paths use), and **includes entries whose md was never written** because the body was too short - `biz_daily` prints `[SKIP] 内容过短` and skips the file while still recording the article, so an entry with no file on disk is expected rather than a dangling pointer. Checked across all twelve days: no article on disk is missing from the JSON, no favorite is in it, and the only entries without a file are those short-content orphans (08-24 has 2, 08-25 2, 08-28/09-02/09-04 1 each, 08-29 2). Six days were rebuilt from their md (2026-08-24, 08-27, 08-28, 08-30, 08-31 and 09-05), each carrying a `reconstructed` block with the reason, the recovered fields, the scope, and the topic verification - and each keeping its original as `.articles.before-reconstruction.json` (09-05's as `.articles.overwritten-by-accidental-run.json`) with its `generated_at` preserved in the new file. **Two mistakes were made and corrected inside this work, and they are the same class**: the first rebuild counted `行动建议.md` as an article, and the first rebuild of four days also pulled in the `收藏/` copies and dropped the short-content orphans - that is, it quietly changed what the file *means* instead of completing it. Both were caught by checking the rebuilt days against the untouched ones. 2026-09-04 is left exactly as it was: its 178 empty topics are the record of the failure this session fixed, and rewriting it would destroy the evidence.
- **Jev cannot rank conversations for search, and this is measured rather than assumed.** The first design of `route_cards` put one card per conversation (type, message count, span, recency, name, query-term hit counts) into a single request and asked Jev which ones were relevant. Both question shapes failed: as a per-card `noul` every candidate landed at 0.50-0.51 (a coupon group with one message sat in the same band as the conference group with 213 hits, and the model left out the session that most deserved opening), and as a per-card `score` on a 0/1/2 scale all 20 candidates scored 1.74-1.76 regardless of whether they had 247 hits or 8. Sorting the same data locally by hit count ranked it correctly. The card simply carries too little for the judgement being asked (the model has never seen the conversation), so the shipped tool **ranks locally and keeps Jev only for the one job it does well**: choosing the real query words from the n-gram fragments. A second `noul` finding is recorded with it - the answer is a **probability float** (0.98 for a true claim, 0.01 for a false one), so reading it as a boolean makes every question look answered "no"; the run printed "it thinks none of these words are what you want" when the truth was that the parser read the wrong field.
- **A limited run still writes a README that describes the whole directory.** `biz_daily`'s README and its `今日简报` are built by scanning the day's existing `.md` files, not from the articles that run fetched, so `--limit 6` on a day that already holds 191 articles rewrites the index for all 191 and reports `共 191 篇推送`. This is not a bug (the README is supposed to describe the day's folder) but it is misleading as a check: a limited test run leaves no trace of its own limit in the README, and the only sign is the count. Use the run's stdout progress lines - not the README - to tell what a partial run actually fetched.
- **`tags` is the configured category for any source that has one, by design.** The prompt for a categorised source is summary-only and explicitly says *不要输出主题、标签、相关度或概念字段*, and the code sets `tags = [category]` itself. Measured over the 1584 articles of the 11 stored days: 1396 carry exactly `[topic]`, 182 carry none, and only **6** carry real extracted tags - and those 6 are the corpus built without configured categories. The checkable signature is that **on every one of those days each source maps to exactly one topic** (36/40/15/43/41/27/35/36/3/36/6 sources, no exceptions), which is what topic-from-config produces and per-article classification does not. A live call through the production prompt returns real tags (`AI与数学, 人类数学家, 数学共同体, 人机关系, 学术人文`), so extraction itself is not broken - it is simply not asked for on that path. Practical consequence: to get meaningful tags for a source, leave its category unconfigured (and accept that its topic then comes from classification rather than from you).
- **No real artifact on disk carries `includeScore`.** The six files in the 2026-09-05 output directory were written before that field existed, so the field has never been produced in a real run - which is why calibration has to re-score articles rather than read stored values.
- The report's admission threshold (`INCLUDE_THRESHOLD = 0.5` on `includeScore`) is provisional in the same way and, unlike the old rule, it is actually applied: both loaders call one predicate. Turning it on **reduced** what the report collects, because the primary loader previously collected everything unfiltered. On a 6-article trial the scores straddled the cut point (0.48 and 0.63 on two engineering posts), so the cut point is doing real work rather than being decorative.
- Message reads select only the columns the reader consumes, resolved per shard from what that shard actually has. `nt_decrypt` reads six (`local_id`, `server_id`, `local_type`, `real_sender_id`, `create_time`, `message_content`) and a WeChat version that renames or drops any other column of the message table therefore cannot make a shard unreadable. What is lost is reported, not swallowed: a shard lacking one of those six is read anyway and named in `missingColumns`, while a shard where none of them is present is reported as `SCHEMA_MISMATCH` and makes `coverage` partial. `export_chat_html` reads rows positionally, so there a missing column keeps its slot as `NULL` instead of shifting the fields after it. Both are verified against synthetic shards only - no future WeChat schema has been tested.

- **Topic exclusion is a display-layer switch, and that is a measurement result rather than a preference.** `dailyExcludeTopics` (or `--exclude-topics`) removes a topic from the daily report and the reader page; the article is still fetched, judged and archived. Filtering *before* the fetch was the original ask and was rejected on evidence: from a source name plus a title and the platform digest - everything that exists pre-fetch - the type judgement agreed with the source-level configuration on only **60%** of 217 articles, with 48 false positives, and there is no gold standard either way. A dropped fetch is irreversible (nothing is archived, and the page is not the same weeks later) while an unwanted article costs only attention, so the decision is deliberately placed where it can be undone by regenerating. The exclusion is orthogonal to `--include-all` and to the inclusion score, and **all three lists in 我拿不准的 are filtered** - passing the exclusion set to `admits()` in the "not admitted" list had the opposite effect and surfaced the excluded articles (that list is populated by exactly the articles being excluded). One predicate (`is_excluded_topic`) now serves both directions. Excluding the focus topic is refused with a WARN, because the result is not an empty report but a misleading one: it exits with "未找到文章，请先运行 biz_daily.py". The key is registered in all four `configService` literals plus `bin`'s `configurableKeys`, which `test/config-keys.test.ts` now enforces - a key missing from defaults or `clear()` survives `config set` and then quietly disappears.
- **The source-level prior is recorded, never acted on.** Every daily appends `(source, topic)` counts for the articles it archived to `~/.weflow-cli/source_topics.json`, and names the sources whose history is stable and lands in an excluded topic (`来源先验: 甲号 → 新闻（20 篇里 19 篇 = 95%）`). **Nothing is skipped.** The table has to be measured rather than authored - the pre-fetch guess it replaces was already measured at 60% - so recording is a prerequisite for a future skip decision, not that decision. It lives outside the repository because it holds 公众号 names (a test asserts this), counts are append-only, and only articles that landed on disk are recorded, so the table and `output/` describe the same corpus. Thresholds (8 samples, 80% share) are **provisional and uncalibrated**. `stable_source_topic` returns `None` for "not enough history yet", and callers must not read that as a default topic - skipping a source *because* it is unknown is the worst failure available here. Whether a stable source is ever skipped before the fetch remains the user's call, to be made on the printed numbers.
## Current Priorities

1. Keep initialization and database access compatible with supported WeChat 4.x variants, with reproducible issue diagnostics that contain no secrets.
2. Keep the daily reader reliable for configured sources and categories without widening access to local data.
3. Maintain security boundaries around local servers, assistant access, MCP tools, and cloud AI disclosure.
4. Evaluate external collaboration through read-only, synthetic-data, versioned interfaces before connecting real user data.
5. Make Bot-channel send capability and its limitations unambiguous in CLI naming and help text before extending messaging features.

## External Collaboration Position

For projects such as Yance, WeFlow CLI remains an independent local data-access layer. Early collaboration may cover read-only schemas, anonymized fixtures, and controlled MCP adapters. It must not require sharing real databases, credentials, keys, full local directories, or direct database access by an external product.
