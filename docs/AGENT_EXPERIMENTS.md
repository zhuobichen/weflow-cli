# Agent 实验记录

本文件记录**对 Agent 做的对照实验**——不是"我改了什么"（那是 `AGENT_ITERATIONS.md`），
也不是"决策是什么"（那是 `DECISIONS.md`），而是**为了验证某个假设而做的可复现实验**：
同样环境、同样任务、不同配置，比较成功率 / 成本 / 速度，用数据决定要不要改产品。

**实验文档不可或缺**：没有它，任何"我觉得这样更好"都无法复核，下次又会凭感觉重做一遍。

## 实验条目模板（每条实验照此写）

```
## EXP-NNN · 实验标题（日期）
- **假设**：一句话说清要验证什么，以及你预期哪个方案更好
- **变量**：只改一个东西（其余完全相同——模型、温度、任务集、环境）
- **对照组**：A（现状）/ B（新方案）/ C（…），每组怎么配
- **任务集**：列出固定任务（可引用 test/eval 的固定用例 id），说明为什么选它们
- **指标**：
  - 成功率：什么算成功（必须有客观判据，不能"看起来对"）
  - 成本：输入/输出 tokens、LLM 调用次数、Jev 调用次数
  - 速度：端到端耗时（p50/p95）
- **控制**：怎么保证"同样环境"——温度固定、记忆清空、无窗口、同一账号数据
- **结果**：表格（每组 × 每指标），原始数据在 `docs/experiments/EXP-NNN-*.json`
- **结论**：假设成立吗？采用/不采用，理由
- **复现**：一条命令或脚本入口
```

## EXP-001 · Jev 预派发工具 vs 现状建议 vs 无 Jev（2026-11-27）

**背景**：用户提出一个架构想法——让 Jev 直接返回该用的工具，harness 派发工具后：
若工具返回的信息已足够回答问题，**就不再把工具列表注入模型**（模型只能基于已取到的
数据作答）；不够时再补工具、这时才注入工具列表继续。对比"去掉 Jev 由模型自己判断"，
看成功率、成本、速度差多少。

**要澄清的设计约束**（来自既有决策，写实验前必须记住）：
- Jev 是 systemone 判断协议，**只返回工具概率，不抽参数、不生成文本**（D-191）。
  所以"Jev 直接派发"只能对**参数可确定**的工具做（词法抽参，如 get_messages 人名+时间；
  或零参数工具如 get_stats）——否则参数从哪来无解。
- 现状已有"Jev 建议 + tool_choice 精确指定概率最高工具"（D-212），那已经是"半预派发"：
  调工具的是模型，只是被强制指定了哪个。D-215 试过全局 `required`+answer_directly 逃生舱，
  失败（模型疯狂调工具不收尾），已回退——本实验不再重复那条死路。

**假设**（待实验验证）：
- H1：预派发（harness 执行工具、信息够时不给模型工具列表）会**降低**模型往返次数与工具误选率，
  因为绕开了"模型决定调不调/调哪个"这个高失败环节。
- H2：它的代价是 Jev 判断错误时浪费一次派发（但 Jev 只给概率，错判成本低于模型乱调）。
- H3：无 Jev 纯模型判断在词法路由兜底下，高频问法不输，但边缘问法成功率下降。

**变量**：工具选择模式（A/B/C），其余固定。

**对照组**：
- A = 现状：Jev 建议注入 + 模型自主调（tool_choice auto）；默认配置
- B = 无 Jev：`assistantJevDoubleCheck=off`，词法路由兜底 + 模型自主调
- C = Jev 预派发：Jev 建议 + harness 词法抽参直接派发 + 信息够时不给工具列表（tool_choice none）

**任务集**：从 `battery-onebyone`（10 条真实场景）+ `battery-adversarial`（9 条对抗）取固定集，
每组跑同样 N 条；用 `--repeats` 多次取平均（模型有随机性）。

**指标**：
- 成功率：答复命中客观判据（must/forbid），与现有 battery 脚本一致
- 成本：每轮 LLM 的 prompt_tokens/completion_tokens（审计 `CLOUD_USAGE`）+ Jev 调用次数
- 速度：端到端 ms（p50/p95）

**控制**：温度 0.4（线上默认）或 0（可复现，二选一写明）、每轮清空记忆、无 GUI 窗口、
同一账号同一数据源、每组之间恢复配置。

**状态**：A/B 两组已跑（2026-11-27），C 组设计完成但因前置条件未实现（见下）。

### 实测结果（2026-11-27，qwen-flash，温度 0，无窗口，同一账号数据）

| 组 | 配置 | 任务数 | 成功率 | p50 耗时 |
|---|---|---|---|---|
| A | Jev on（现状建议注入） | 10 | **7/10** | **63.9 秒** |
| B | Jev off（词法路由兜底 + 模型自主） | 20（2 repeats×10） | **17/20 = 8.5/10** | **5.3 秒** |

原始数据：`_tools/tmp/exp001-A.json` / `exp001-B.json`（本地临时，不入仓）；runner 在
`_tools/wx-mirror/exp-runner.mjs`（不入仓，可按需重建）。

### 关键发现：A 组慢 12 倍的根因是 Jev 端点，不是架构

审计日志显示 A 组每次 `JEV_MULTI on none model=?`——**Jev 返回空建议、模型字段丢失**，
且相邻两次 JEV_MULTI 间隔固定 **~64 秒**（13:02:38 → 13:03:42 → 13:04:46…），
而 JEV 之后 2-4 秒就完成 LLM 调用。结论：
- 那 60 秒是 **Jev 判断层调用的超时/重试**，不是 LLM、不是工具执行；
- `model=?` + `none` 说明 Jev 端点（302 中转 `/typesafeai/v1`，见 AGENTS.md）此刻**不可达或返回异常**，
  代码按设计静默降级（"判断失败不影响对话"），但代价是每次多等 60 秒。

所以"Jev vs 无 Jev 的速度差"这个测量结果，**反映的是当前 Jev 端点故障，不是 Jev 架构的理论速度**。

**阳性对照（2026-11-27）**：直连 Jev 端点 `https://api.302ai.cn/typesafeai/v1/systemone`
（用 `buildMultiRequest` 生成的真实请求 + typesafeApiKey），**30.9 秒后返回 HTTP 502 Bad Gateway**。
这坐实了"端点故障→静默降级→每次多等 60 秒"的链条，不是我们臆测。
要测架构本身的差异，得先用可用的 Jev 端点重跑 A 组（待办）。

### 成本指标：本次无效（记录为方法缺陷）

runner 用 `tail -800` 抓 `CLOUD_USAGE` 审计算 before/after 差值，但审计日志是滚动的，
任务执行期间旧行被挤掉，导致差值为负（`calls: -4, inTok: -29273`）——**成本数据作废**。
修正方法：改为每轮从 API 响应体直接读 `usage`（`/api/ask` 目前不透传，需要在后端加字段），
或在实验开始前把审计日志复制到独立文件再比对。下次实验必须修这个，否则"成本"结论不可信。

### C 组（Jev 预派发）未实现——前置条件与决策

用户设想的 C 组需要：Jev 建议 → harness 按建议**填参数并执行** → 信息够则不给模型工具列表。
但两个硬约束让它无法在 API 层干净模拟：
1. Jev 只返回工具概率、**不抽参数、不生成文本**（D-191）——参数只能靠词法抽参，
   仅覆盖 get_messages 人名+时间等少数工具，其余工具无解；
2. "信息够不够回答"本身需要一次判断（模型或规则），若用模型则抵消了"预派发省往返"的收益。

且 D-215 已证明全局 `required`+逃生舱会让小模型疯狂调工具不收尾（已回退）——那条死路不再重复。

**决定**：不在产品代码里加实验专用开关（污染主线、且实验失真风险高）。C 组的验证推迟到：
(a) Jev 端点恢复可用；(b) 明确"信息够不够"的判据（建议先用规则：工具结果非空且含任务关键词即视为够）；
(c) 以独立分支实现，不进 master。在此之前，A/B 数据已能回答用户问题的主要部分。

### 对原始问题的回答

"Jev 预派发 vs 去掉 Jev 由模型判断的区别在哪"：
- **理论区别**：前者把"调不调/调哪个"从模型（概率、会偷懒）移到 Jev（确定性建议）+ harness（直接执行），
  代价是 Jev 判断错误时浪费一次派发、且 Jev 不抽参限制了可派发的工具范围。
- **本次实测**：Jev on 反而更慢（端点故障）、成功率并未更高（7/10 vs 8.5/10）——
  在这台机器当前状态下，**无 Jev + 词法路由兜底的 B 组是更优选择**（这也正是当前默认配置）。
- **不能下的结论**：不能说"Jev 架构本身更差"——本次 A 组数据被端点故障污染。
  要公平比较，需先修 Jev 端点再重跑。
