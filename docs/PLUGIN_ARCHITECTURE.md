# 插件架构（预定）

这一页回答两个问题：**插件层到底解决什么**，以及**它应该分成哪几层、现在到哪一步**。
契约细节在 [PLUGIN.md](PLUGIN.md)，取舍理由在 [DECISIONS.md](DECISIONS.md) 的 D-048 / D-137 / D-138。

## 一、插件不是"方便合并"，是"把变化关进契约里"

"有了插件，别人扩展功能就很方便"这句话对了一半，而错的那一半会让人做错决策。

**它对的部分**：插件让第三方**不改你的代码**就能加能力。核心不再为每一个第三方需求改动。

**它错的部分**：插件并不降低"改东西"的总成本，它只是把成本**换了位置**。

- 没有插件时，痛在两个地方：①核心被一堆互不相关的需求污染；②每加一个功能，都要重新理解整个仓库。
- 有了插件，①消失了，②对**插件作者**依然存在（他要理解契约），而核心多出一个新负担：**契约本身变成了不能随便改的东西**。

所以真正的判断标准不是"要不要插件"，而是：

> 这个扩展面的变化频率和参与人数，是否高到值得为它冻结一份契约？

值得冻结的，通常是**能力可枚举、数据边界清楚**的扩展（加一个工具、接一个内容源）。
不值得的，是**需要深度耦合内部状态**的功能——那种做成插件只会得到一份假装解耦的契约，
然后每隔一个版本就被绕过一次。

这就是为什么这个项目的插件是**进程外**的：能冻结的只有"数据进、结果出"这条边界，冻结不了内部状态。

## 二、对照 DSH：同样是插件，为什么形态必须不同

DSH 的插件层是完整的，可以直接当参照物。它由四件套组成：

| 层 | DSH 的对应物 | 作用 |
| --- | --- | --- |
| 加载 | `cordis-plugin-loader` | 把插件装进**同一个进程** |
| 生命周期 | `dsh-plugin-manager`（按 profile 共存） | 启用/禁用/切换 |
| 清单 | `host-plugin-inventory` | 现在装了什么、哪些可用 |
| 分发 | `plugin-market` + `settings-plugins` UI | 发现、安装、配置界面 |

**WeFlow 不能照抄的是第一层。** cordis 的插件跑在主进程里，和宿主共享内存、对象和权限；
DSH 可以这么做，因为它是一个开发工具，插件作者与使用者基本是同一类人，信任模型成立。
WeFlow 持有**解密后的微信数据库、含全部密钥的配置和消息通道**——同一形态在这里不是架构选择，
而是安全回退（D-048 已把这条写死）。

代价要认：进程外拿不到进程内的便利（共享对象、直接调内部 API、低延迟）。
换来的是能力上限清楚、边界可验证。**这个交换是刻意的，不是没做完。**

所以 WeFlow 的"分发层"（market）在架构里**排在最后**，而且要按"清单 + 文档"的轻形式做，
不做需要为别人代码背书的中心化市场。

## 三、预定的分层架构

```text
┌─────────────────────────────────────────────────────────┐
│ 6. 分发  发现 / 版本兼容 / 文档 / 示例        ← 部分（GitHub topic，无市场）│
├─────────────────────────────────────────────────────────┤
│ 5. 校验  产出交给真消费端验证                 ← 已实现（知识源卡片）        │
├─────────────────────────────────────────────────────────┤
│ 4. 权限  环境白名单 / 确认门 / 单独禁用        ← 已实现                      │
├─────────────────────────────────────────────────────────┤
│ 3. 宿主  注册表 / 生命周期 / 超时 / 故障隔离   ← 已实现（无热重载）          │
├─────────────────────────────────────────────────────────┤
│ 2. 传输  stdio MCP（工具）/ stdin 作业（采集） ← 已实现                      │
├─────────────────────────────────────────────────────────┤
│ 1. 契约  weflow-plugin/1 清单 + 卡片格式       ← 已冻结，缺版本协商          │
└─────────────────────────────────────────────────────────┘
```

**顺序不能颠倒。** 越靠下越难改：第 1 层一旦有第三方依赖，改它就要付兼容代价；
第 6 层换一种做法则几乎无成本。所以设计的力气应该压在下三层。

### 第 1 层：契约（最贵的一层）

- 清单：`schema` / `id` / `kind` / `entry` / `permissions`。
- 卡片：frontmatter + `## AI 摘要` + `[[name]] — 描述`（由 `compile_wiki` 消费）。
- **冻结的是形状，不是实现**：插件用任何语言写都行，只要说这个协议。

缺口：现在是**单版本严格匹配**——高于本机的说"请升级 weflow-cli"，低于本机的说"旧契约不再支持"。
还缺"宿主双读一个版本"的兼容窗口：升到 v2 时，v1 的插件应该继续能跑一个版本，
那样第三方才有时间跟进。（这条已写进第 4 节的待办，不是遗漏。）

### 第 2 层：传输

两种，各有各的理由，别合并：

- **工具插件 → stdio MCP**：因为客户端只认 MCP，而且进程边界天然存在。
- **知识源插件 → stdin 作业 + 一个输出目录**：因为它不是请求/响应，是"跑一次、产出一批文件"。
  硬包装成 MCP 工具会得到一个只能返回超长文本的工具。

### 第 3 层：宿主

注册表（`~/.weflow-cli/plugins.json`）、按需连接、超时、故障隔离——已实现。
一个起不来或握手挂住的插件只让它自己消失，不让工具表不可用（有测试钉住）。

缺口：没有热重载。改了插件要重启 MCP 服务，因为连接是缓存的。
这是刻意的（重启比"猜什么时候该重连"可预期），但要在文档里说清楚。

### 第 4 层：权限

三条宿主强制的边界：进程外、环境白名单、默认确认。加上"单独禁用"。

**这一层的关键不是"能拦什么"，而是"不假装能拦什么"。**
清单里的 `permissions` 只展示、不强制——把声明当保证，就是在重复 D-048 批评过的错误。

### 第 5 层：校验

知识源插件的产出交给**真的消费端**读一遍（`plugin_card_lint.py` 调 `compile_wiki` 自己的解析函数）。
不在 TypeScript 里重写一遍规则——那是第二份契约，Python 那边改了不会红。

这一层值得单独存在，因为卡片最贵的失败是**静默的**：没有 wikilink 的卡片会被跳过，
文件在、目录在、什么都不报错。只有消费端能回答"这张卡到底有没有用"。

### 第 6 层：分发

现在：GitHub topic `weflow-plugin` + 文档里一份清单。
**不做中心化市场**——它意味着为别人的代码背书，维护成本和安全责任都不划算。

真正该补的是**兼容矩阵**：插件声明"我要求哪一版契约"，宿主声明"我支持哪一版"，
不匹配时给一句人能看懂的话。这是别人敢写插件的前提，比市场重要得多。

## 四、还差什么（按值得做的顺序）

1. **契约版本协商**：插件的要求 vs 宿主的支持，向前/向后都给出可读结论。
2. **插件清单自省**：`plugin list --json` 已经够用，缺的是"这个插件会改哪些文件"的可核对形式。
3. **热重载**（低优先）：改插件要重启，写清楚即可，不必实现。
4. **中心化市场**（不做）：除非重来一次把它设计成"只做索引、不做托管"。

## 五、一句话结论

插件的价值不在"加功能更容易"，而在**"加功能不需要动核心，因而核心可以保持小"**。
它成立的条件是契约够窄——窄到能被冻结、能被验证、能被第三方在没有你帮助的情况下猜对。
所以这张架构图里最该花时间的永远是第 1 层和第 5 层，而不是第 6 层。
