# weflow-cli Agent 迭代记录（反馈学习用）

这份文档记的是**迭代过程**——用户反馈了什么、我怎么排查、试过什么、什么没用、最后学到什么。它和另两份文档互补：

- [DECISIONS.md](./DECISIONS.md)：每个决定的最终形态与理由（ Decision / Reason / Alternatives）。
- [CHANGELOG.md](../CHANGELOG.md)：面向用户的发布说明。
- **本文**：过程中的试错与教训——**"什么没用"比"最后做了什么"更值得记住**，避免下次重蹈覆辙。

每条迭代的结构固定为：**触发 → 排查 → 试过但没用 → 结论 → 教训**。按时间倒序（最新在上）。

## 2026-11-05 · 悬空概念补页选"抽取式"而非模型生成（从 commit-msg-fill.txt 提炼）

**触发**：知识库有 5,716 个"被引用但没有页"的概念目标（8,098 条链接）。

**试过但没用（设计阶段就想清楚的）**：原方案调模型逐页生成——① Jev 是 systemone 判断协议，
不生成文本，做不了；② 让普通模型写 5,716 页，成本高且会编造；③ 大量名字在卡片语料里
**一条材料都没有**，对它们"生成"就是编。

**结论**：`scripts/fill_dangling.py` 改成抽取式——只用卡片正文里的**完整原句**拼页，
每句带出处链接；按"被多少页提到"排序；一张卡只贡献一句；没材料的名字跳过并计数
（"补不了"本身是信息）；dry-run/apply 分离。实测 top300 里 218 个（73%）能找到原文材料。

**教训**：**当材料不足时，"抽取"比"生成"诚实**——尤其知识库补页这种场景，宁可跳过并计数，
也不要让模型编出一段看起来像定义的文字。第一版按字符截取把定义切在半句，改成取完整句子——
**截断的定义比没有更糟**。

（注：此条从 `output/commit-msg-fill.txt` 草稿提炼，脚本已在 git commit `639e70d`。）

## 2026-11-26 · wiki compile 走已配置的 AI 通道（不再硬要 DeepSeek key）

**触发**：服务器上跑 `weflow-cli wiki compile --yes` 报"需要 DeepSeek key"，但服务器配了可用的中转 key（dashscope/qwen-flash）。

**排查**：CLI 的 wiki compile action 把 `apiKey: opts.apiKey` 直接传给 Python（只认命令行 `--api-key`），没走模块里已有的 `resolveAiKey()`——那个函数已正确处理"显式 > 环境变量 > (aiBaseUrl时)aiApiKey > deepseekApiKey"的优先级。Python 侧 `call_deepseek` 本来就尊重 `aiBaseUrl`，key 一传对就走中转端点。

**结论**：wiki compile 的 apiKey 改走 `resolveAiKey(opts.apiKey)`，不带 `--api-key` 也能用配置里的通道。

**教训**：仓库里已有统一的 key 解析函数时，新命令要复用它——单独写 `opts.apiKey` 就漏掉"配置里的 key"这条默认路径。同一个坑在别的命令上可能还在。

## 2026-11-26 · 给自建 harness 标明定位与阶段

**触发**：用户澄清自建 harness 的定位，并要求标注它处于初步阶段。

**结论**：在 [AGENT.md](./AGENT.md) 与 README 写明：自建 harness 是一个**完整的 harness**，轻量化、专为微信适配；设计出发点是**持久化独立部署**。目前处于**初步阶段**——循环、记忆、判断仍在打磨，接口与行为可能调整。这一整晚的迭代（D-194~205）都在这条线上。

**教训**：文档里的定位措辞要以所有者表述为准——"完整但轻量的 harness、为持久化独立部署而生"，别自行降级成"适配层"或添油加醋。阶段标注（初步）与能力定位（完整 harness）是两件事，不要混为一谈。

## 2026-11-26（跨零点）· 一轮"防御过度 → 红线"的完整反转

**触发**：用户连续反馈——"默认全放开，都读完吧，每次都是遇上这些问题，防御过度了"；随后"硬规则不要限制这么多，模型够智能了，作红线限制即可"；再后来"直接强制调用吧，调多调少以后研究，能做正确就 OK"。

**排查与试错链**（这一轮最关键的价值全在这里）：

1. 隐私 `strict→balanced→open` 一路放开，但用户仍反复看到"（这一轮我给出的具体事实被校验拦下了，内容不可靠…）"。排查发现**这不是守卫写的**，审计 `GUARD_CHECKED fired=0`，是模型从记忆里学来后自己复述的占位话术。→ 结论：清记忆治标，系统提示里禁掉这类内部话术才治本（D-196）。
2. 守卫默认关（D-195）后，**模型开始不查就答**——问"白马非马发了什么文件"答"没有"，实际有 `figure (2).pdf`。先后试过：① 提示词里加"点名联系人就用 get_messages"——用户明确反对（提示词多是限制），**撤回**；② Jev 建议作为参考信号注入——模型**照样无视**，零工具作答。
3. 用户拍板"直接强制调用"→ 在 ReAct 循环里加硬约束：**Jev 建议了工具但零调用 → 丢弃答复、回炉一次**（D-202）。这才真正解决。教训：**软提示压不住就别反复加提示词，要么给红线，要么承认模型能力边界**。
4. 词法快路径同样的问题：它把"关于某人的聊天记录"错派给知识库搜索。我本能地又加了一条兜底正则——用户当场制止："硬规则不要限制这么多"。→ 撤回补丁，**词法默认关**（D-197），交回模型。教训：**"加一条规则修一个句式"是补丁思维，下一个句式还会撞**。
5. 后来又出现严重幻觉：`read_favorite` 明明返回"未找到"，模型却编出整篇摘要（含 2.5~3.8 倍等数字），下一轮又说没有——前后冲突。同样地，提示词里早写了"查不到就说查不到"但无效。→ 加确定性判据：**工具说未找到 + 答复给具体标题/数字/来源 → 顶回去**（D-205），仍独立于守卫总开关。教训同 3：**确定性文本判据 > 反复加提示词**。

**贯穿这一轮的教训**：
- 用户要的"全放开"不是无政府，是**"防御退到几条红线"**——守卫默认关、隐私 open、词法关，但保留"Jev 建议必调工具""未找到不许编"这类红线。
- **判断层建议如果只是"参考"，模型会无视**；要它生效就得做成强制，或者承认它只是日志。
- 三次都是"先加提示词/补丁 → 无效 → 用户制止 → 改成结构性机制"。**下次遇到模型不配合，先问：这是提示词能解决的，还是需要一条确定性判据？**

## 2026-11-26 · 文档门户化与架构图

**触发**："README 写得跟操作文档一样，GitHub 是门户，很影响观感"；"架构图不用强制风格"。

**试过但没用**：
- 用 MiniMax 按 cm-cel-boil（逐帧手绘 / 线条沸腾）风格生成架构图 → 手绘风好看但**文字错乱**（"CHON""DBB"），信息表达不可靠。
- 换中性简约风格重生成 → 图更淡、文字依旧乱码（"JEOMNES""MEMUM"）。
- 结论：**文生图做技术架构图，文字必然不可靠**，换风格解决不了。

**结论**：写 `weflow-agent-architecture.svg` 作为**可维护源**，用 sharp 精确渲染成 PNG——文字 100% 准确，改结构只改 SVG。README 收敛为门户（Agent 段落 5 行 + 指路），细节拆到 [AGENT.md](./AGENT.md)。

**教训**：**需要精确文字的图（架构图、流程图）不要依赖文生图**；AI 生图适合氛围/装饰，不适合信息承载。有 SVG 源 + 精确渲染这条路时，别绕道生图。

## 2026-11-25 · 测试污染：每个版本必须从干净会话开始

**触发**：换版本测试时行为像没换；"你能看这个 pdf 吗"反复答"没有"。

**排查**：逐个排除——模型太烂？Jev 没注入？隐私没生效？配置时序？agent 缓存？最后用 A/B 定位：**同一模型、同一 dist、同一问句，干净 userId 选对工具，固定桶 `wxmirror-sidebar-2` 选错，清桶后选对**。根因是记忆桶里攒的旧问答关联让模型照着复述。

**试过但没用**：反复清记忆——清完又被测试本身重新写入，形成循环。

**结论**：做 `fresh-test.mjs`——每版测试前备份 trace 到**本地**（不上传）、清空记忆桶、重启助手与后端。约定"测试时别用同一问句反复问"。

**教训**：**测试隔离是版本可比性的前提**；"清一次"不够，要把"清"变成每次测试前的固定动作。另外：判断"是不是模型问题"时，用**干净上下文的 A/B 对照**比反复猜快得多。

## 2026-11-25 · 窗口标题"变回微信镜像"——猜错方向的典型

**触发**：harness 窗口打开时标题对，点一下就变回"微信镜像"。

**试过但没用（全是猜）**：换独立 profile、换时间戳 profile、服务端按 URL 注入 title、改启动脚本关窗口匹配……折腾好几轮，标题还是会变。

**真根因**：UI 自己的 JS——`window.addEventListener('focus', ...)` 里有 `document.title = '微信镜像'`（未读消息提醒逻辑），**用户点窗口触发 focus 就把标题改回去**。与 profile 缓存无关。

**结论**：标题基准按模式走，`BASE_TITLE = AGENT_ONLY ? 'weflow-cli harness' : '微信镜像'`，focus/blur 都用 BASE_TITLE。

**教训**：**"运行时什么东西改了它"要先于"缓存/环境"类猜测**。遇到"值变了"，第一反应应该是 grep 谁在写这个值（`document.title`），而不是猜浏览器行为。这次把简单问题复杂化了。

## 2026-11-25 · "力求什么都能看"——文档读取能力

**触发**："不仅加 read_pdf，read_word 也加上，力求什么都能看"。

**过程**：
- 做成**一个** `read_document` 工具按扩展名分派（而不是每个格式一个工具——工具表会膨胀、模型选择变差）。
- 全量体检服务器微信文件目录 2120 个文件：真文档 96 个。第一轮体检 94/96，老格式 `.doc` 35 个 + `.xls` 1 个全失败。
- 补 `.doc`：`antiword` 优先，但 1 个 WPS 生成的 .doc 它认不出 → fallback `catdoc` 解决。补 `.xls`：`xlrd`。最终 96/96。
- 省略句"这个 pdf"读不到：模型知道文件名却猜错路径 → 加 `--name` 按文件名在微信文件目录递归定位真实路径（D-203）。

**教训**：**"全量体检"比"抽样测几个"可靠**——第一轮如果只测 pdf/docx 就发现不了老格式全军覆没。依赖装在服务器（antiword/catdoc/xlrd），换机器要重装——这类系统依赖记在文档里。

## 怎么记录下一次迭代

在本文顶部加一条，结构照上面：**触发（用户原话）→ 排查 → 试过但没用 → 结论 → 教训**。

- **"试过但没用"必写**——这是反馈学习的核心，DECISIONS.md 的 Alternatives 太简，装不下试错过程。
- **教训写成可迁移的原则**，不要只写这次改了什么。
- 最终决定同步进 DECISIONS.md（编号连续）；用户可见变化同步 CHANGELOG.md；能力/限制变化同步 [PROJECT_STATE.md](./PROJECT_STATE.md) 与 [AGENT.md](./AGENT.md)。
- 代码侧改动记进 git commit message（squash 后的那条），本文记**过程**。
